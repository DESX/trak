# Conformance vectors

Shared test vectors that every trak implementation must pass. They are generated by
[`generate.py`](generate.py) (`python conformance/generate.py` from the repository root,
with the Python package's dev dependencies installed) and reviewed by hand against
[SPEC.md](../SPEC.md). CI regenerates them and fails if anything changes.

| Folder | Contents | An implementation passes when |
|---|---|---|
| `valid/` | `NAME.trak`, `NAME.expect.json` | decoding the file gives exactly `expect.json`, and `check` passes |
| `invalid/` | `NAME.trak`, `NAME.reason.txt` | `check` fails, ideally at the stated offset |
| `write/` | `NAME.input.json`, `NAME.trak` | replaying the input reproduces the `.trak` byte for byte |

Every write vector's `.trak` is also a valid vector with the same name.

## `expect.json`

```json
{
"types": [
  {
    "name": "build", "index": 1, "version": "1.0",
    "description": "One CI build run.",
    "parsed": true,
    "annotations": [],
    "fields": [
      {
        "path": "tags.[]", "type": "str", "enum": [], "unknown": null,
        "block": false, "optional": false,
        "annotations": [{"name": "ms", "text": null}],
        "description": "who triggered the build"
      }
    ]
  }
],
"events": [
{"type": "build", "n": 1, "timestamp": "20261107T140210.120Z", "value": {"user": "ana", "error": null}}
]
}
```

- `types` are in index order. `parsed` is false when a reader can't parse the definition
  (SPEC §9). The type still navigates, its `fields` are empty, and its events' `value` is `null`.
- `annotations` on a type are those on its top-level object.
- Field `path`s write list indexes as `[]` and map keys as `{}`. `type` is `str`, `num` or
  `enum`. An unknown leaf has type `str` and keeps its original text in `unknown`.
  `optional`, `annotations` and `description` follow docs/DECISIONS.md (I1–I3).
- `events` are in file order. Leaf values are strings holding the raw bytes (every vector is
  UTF-8), and absent values are `null`. Objects are JSON objects. Lists are arrays. Maps are
  arrays of `[key, value]` pairs in file order, and a key is `null` when its entry has no
  leaves (D3).

## `reason.txt`

The first line says what is wrong. An optional `offset: N` line gives the byte offset
where the Python reference `check` reports the problem. Other implementations should fail,
and may report a different offset.

## `input.json`

A list of operations, applied in order to a new file:

```json
[
{"op": "define", "name": "build", "schema": "{ user: str }\n"},
{"op": "write", "type": "build", "value": {"user": "ana"}, "timestamp": "20261107T140210.120Z"}
]
```

Values use the same shapes as `expect.json`, with two differences. `num` leaves may be JSON
integers within 64 bits (signed or unsigned) or decimal strings. Maps are always `[key, value]` pairs, so that entry order is
explicit in every language. Timestamps are always given, so output is deterministic.

## Vectors

| Name | Covers |
|---|---|
| 001-spec-example | the SPEC §13 example, byte for byte |
| 002-magic-only | a file with no objects |
| 003-type-without-events | a type with no events; dir pointer to a schema |
| 004-empty-lists-and-maps | empty lists and maps write nothing |
| 005-absent-optionals | absent optional values, including missing keys |
| 006-block-forged-structure | block values holding exact footer and label lines |
| 007-inline-lf | an inline value containing LF |
| 008-utf8 | multi-byte UTF-8 values and map keys |
| 009-map-key-punctuation | map keys with `.`, `:`, `]`, spaces, and an empty key |
| 010-many-types | 35 types, so dir types need two-letter VLQs |
| 011-long-values | lengths 675 and 676 (two- and three-letter VLQs), a 20 KB block |
| 012-schema-long-before | a schema defined 200 events before its first event |
| 013-deep-nesting | lists of objects with maps of lists |
| 014-chain-10000 | a 10,000-event chain |
| 015-interleaved | four types interleaved, exercising the directory policy |
| 016-num-forms | integers, big integers and every decimal form of `num` |
| 017-enums-annotations | enums with trailing commas; annotations with text |
| 018-descriptions | type and field descriptions, including the last-key-on-a-line rule |
| 019-empty-objects | `{}` fields, lists and maps of empty objects (D6) |
| 020-keyless-map-entries | map entries whose key isn't recoverable (D3) |
| 021-empty-strings | empty inline and block values |
| 022-optional-containers | optional lists, maps and objects (D1) |
| 023-same-timestamps | equal timestamps within a type; types in different eras |
| 024-blocks-in-lists | `[] \|str` and map of blocks |
| 025-top-level-annotation | annotations on the event's top-level object |
| 101-torn-tail | a torn body after the last object (SPEC §11) |
| 102-torn-tail-partial-footer | a torn tail ending in half a footer |
| 103-extensions | `E > 0` in schema and event footers |
| 104-unknown-leaf-and-annotation | unknown leaf types and annotations in a 1.2 schema |
| 105-newer-minor | a newer minor in the magic line and a schema footer |
| 106-unparseable-newer-schema | a schema a 1.0 reader can't parse still navigates |
| 107-other-dir-policy | a writer whose directory always points at schemas |
| 108-self-dir | a dir type equal to the event's own type |

Invalid vectors cover:
- a bad magic line and an unknown major
- a body length past the file start, and a walk that misses the footer
- a bad VLQ letter, and a VLQ with a leading zero
- a pointer to the wrong type, and a wrong dir pointer
- a duplicate schema name, a schema index gap, and an event before its schema
- a bad `num`, a bad `enum`, and a bad block label
- decreasing timestamps, an impossible timestamp, and a wrong event number
- a 1.0 schema with a syntax error
